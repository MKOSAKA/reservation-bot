# 予約代行の手順書（AI 向け）

ユーザー（マスオ）から「予約取って」と頼まれた AI が、この手順だけで代行できるように書いた運用手順書。
スマホの Claude アプリなど、PC を使わない会話から依頼される前提。回答は日本語。

> 正本はこのファイル。`CLAUDE.md` はここへの入口だけを持つ。手順を変えたら本ファイルを PR で更新する。

## 0. 全体の流れ

```
聞き取り → 予約受付の開始日時を確認 → YAML 作成・検証 → ユーザー確認 → PR → ユーザーの「マージして」でマージ
→ GitHub Actions がサーバへ登録（Slack に通知）→ 開始日時にサーバが自動予約 → 結果を Slack #予約ボット に通知
```

AI 自身は予約サイトを操作しない。予約の確定はサーバ（EC2）のデーモンが開始時刻に行う。

## 1. 対応施設

| サイト | 施設キー | 自動予約 | 備考 |
|---|---|---|---|
| スタジオル | `studiol` / `base-on-top-umeda`（ベースオントップ梅田店） | **可**（2026-10-05 実予約試験合格・自動確定許可済み） | 下記 |
| LaBOLA | `labola` / `morinomiya`（フットサル もりのみや） | **不可** | クラウドからの予約導線が 403（アクセス制御）。回避しない。ユーザーに手動予約を案内する |

上記以外は「未対応」と伝えて登録しない（新規対応は別途開発）。

### スタジオル（ベースオントップ梅田）

- 部屋: `1st`〜`8st`。`2st`・`5st`・`8st` は30分開始（:00 を指定すると自動で :30 にずれる）
- ユーザーの定番: **土日祝、1st > 8st > 7st、12:00〜18:00 の間で2時間**
- 人数: バンドごとに違う（6〜10人が多い）。**毎回聞く**（既定 8）
- 料金: 1st 2時間 8,300円（2026-10-05 実績）。料金上限 `max_price` は任意（超えたら確定しない）
- 予約できる範囲: 「Web 予約は3か月後の月末まで」。**開始日時は未確定**（仮に毎月1日 0:00。2026-11-01 前後に観測して確定する）
- キャンセル規定: **利用日の3日前までは無料**。前々日・前日・当日は100%。キャンセルはユーザー本人がマイページで行う

## 2. 聞き取り

必須: 日付 / 開始時刻の希望（複数なら優先順）/ 利用時間 / 部屋の優先順 / 人数。
省略されたら定番（上記）を提案して確認する。曖昧なまま登録しない。

## 3. 予約受付の開始日時を確認する

- `npx tsx src/cli.ts validate config/requests/<id>.yaml` の出力（開始日時・候補・警告）で確認する
- **開始日時がすでに過ぎている日（＝もう予約できる日）は自動予約の対象外**。
  デーモンは「開始時刻を過ぎて起動した」として実行しない（安全側の設計）。
  → ユーザーに手動予約を案内する（空き状況だけなら AI がブラウザで確認してもよい）
- 開始まで70分未満も、サーバの起動が間に合わない可能性があるため手動を案内する

## 4. YAML を作る

`config/requests/<id>.yaml`（**id = ファイル名**。英小文字・数字・ハイフンのみ。例 `2027-02-13-umeda`）

```yaml
id: 2027-02-13-umeda
provider: studiol
facility: base-on-top-umeda
date: 2027-02-13
duration_minutes: 120
room_priority: [1st, 8st, 7st]
time_priority: ["14:00", "13:00", "15:00", "12:00", "16:00"]
time_first: false        # false = 部屋の優先を先に（1st の全時刻 → 8st …）。true = 時刻の優先を先に
people: 9
earliest_start: "12:00"
latest_end: "18:00"
max_price: null          # 例: 9000（超えたら確定しない）
mode: auto
```

- 時刻は必ず引用符で囲む
- `release` は省略（施設の既定を使う）
- `mode: auto` で開始時刻に確定まで行う。確認画面で止めたいとき（試験など）は `assist`

## 5. ユーザーの確認 → PR → マージ

1. `validate` の出力をそのまま見せ、「この内容で登録してよいか」を聞く
2. ブランチ `ai/claude/request-<id>` で PR を作る（本文に依頼内容と validate の出力）
3. **ユーザーの「マージして」を待ってからマージする**（包括的な「任せる」では代行しない）
4. マージで GitHub Actions `register-requests` が動き、サーバ起動 → 登録 → Slack `#予約ボット` に「📝 予約リクエストを登録しました」
5. Actions の結果を確認して報告する。失敗時はログを見て原因を伝える（再実行は `workflow_dispatch`）

## 6. 当日の動き（ユーザーへの説明用）

- 開始の24時間前と10分前に、サーバが自動起動してログインと設定を確認（結果を Slack へ）
- 開始時刻ちょうどに空きを取得し、候補を優先順に試して確定。結果を Slack へ
  - ✅ 予約成功（予約番号・部屋・時間・料金）
  - ❌ 予約失敗（全候補が埋まっていた等）
  - ⚠️ 要対応（ログイン失敗、サイト変更、確定後に結果を確認できない等）→ ユーザーがマイページを確認・手動対応
- 終われば自動停止する

## 7. 取り消し・変更

- **登録済みリクエストの取り消し**: 現状はサーバ上の CLI のみ（`cli.sh cancel <id>`、AWS CloudShell から SSM 経由）。
  スマホの会話からは実行できないため、ユーザーに CloudShell での実行を案内するか、PC での作業時に行う
- **変更**: 取り消し → 新しい id で登録し直す（同じ id の上書きは状態によって拒否される）
- **確定済み予約のキャンセル**: ユーザー本人がスタジオルのマイページ「予約のキャンセル」で行う（AI は行わない）

## 8. AI がしてはいけないこと

- 予約サイト上で予約の確定・キャンセルを操作する（サーバのデーモン、またはユーザー本人が行う）
- `STUDIOL_ALLOW_SUBMIT` / `LABOLA_ALLOW_SUBMIT` など確定可否の設定を、ユーザーの明示指示なしに変える
- CAPTCHA・WAF・アクセス制御を回避する（`AGENTS.md`）
- パスワード・Cookie・Webhook URL をチャット・ログ・Git に出す
