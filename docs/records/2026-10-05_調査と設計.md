## 4. アーキテクチャ

### 実行基盤の比較

| 案 | 解禁時刻の精度 | 事前準備（T-10m） | ブラウザ | 状態保持 | 判定 |
|---|---|---|---|---|---|
| 常駐VPS/EC2 + systemd | ◎ chrony で ms 級・プロセスが先に起動して待機 | ◎ 同一プロセスでログイン・ページ preload | ◎ | ◎ ローカルディスク | **採用** |
| Lambda / Cloud Run Jobs + Scheduler | ○ 起動は分単位。T-5m 起動→待機なら可 | △ 実行時間上限・コールドスタート | △ Chromium 同梱が重い | △ S3等へ外出し | 次点（コスト最小化時） |
| GitHub Actions cron | × 数分〜数十分の遅延・スキップあり | × | ○ | × | CI専用 |
| Fly.io / Railway | ○ | ○ | ○ | ○ | 新規ベンダー契約が増えるため見送り |
| 既存 MCP 用 EC2（t4g.micro）に同居 | ○ | ○ | △ メモリ916MB・OOM 実績 | ○ | 障害が MCP 全体へ波及するため不可 |

### 決定

| 項目 | 決定 | 理由 |
|---|---|---|
| runtime | Node.js 22 + TypeScript + Playwright(Chromium) | 指定どおり。DOM 操作が必要な予約フローに適合 |
| host | 専用 EC2 t4g.small（arm64・2GB）Ubuntu 24.04、SSM のみ（SSH閉鎖） | Playwright 公式対応 OS。既存 AWS 運用（SSM・Secrets Manager）を踏襲。月額概算 $16 前後（t4g.micro 約$8 の2倍） |
| scheduler | 常駐デーモン（systemd `Restart=always`）が T-24h / T-10m / T-15s→T0 を管理 | cron は準備時間を持てない。フェーズ発火は DB で一意化 |
| 時刻 | chrony + Amazon Time Sync Service、T-10m に offset を確認（>0.5s で通知） | 秒単位の安定起動 |
| database | SQLite（WAL） | 単一ホスト・単一ライター。条件付き UPDATE と UNIQUE 制約で冪等性を担保。Web UI 化時に Postgres へ移せるよう Store に閉じ込め |
| secret | Secrets Manager → ホスト側スクリプトで `/etc/reservation-bot/env`(0600) へ展開。storageState は 0600＋AES-256-GCM、EBS 暗号化 | 既存 MCP 基盤と同じパターン |
| notification | Slack Incoming Webhook（push）。LINE Messaging API・Discord も選択可 | （10/05 更新）通知先は本人のみのため Slack Incoming Webhook を第一候補に変更。LINE/Discord も実装済みで任意 |
| browser automation | Playwright。selector は name属性・class名・テキストを使い、nth-child に依存しない | 公開カレンダーは安定した class/data 属性あり |
| deployment | GitHub → SSM で `git pull && npm ci && npm run build && systemctl restart`（手動） | 組織方針: デプロイは手動 |

### 二重予約防止

1. auto 実行は `scheduled|preflight_ok → running` の条件付き UPDATE に成功した1プロセスのみ
2. `reservations.request_id` UNIQUE
3. 実行前にサイト上の既存予約を照合（マイページ）
4. 予約送信後に結果を確認できない場合は他候補へ進まず `manual_intervention_required`
5. デーモンは PID ロックで単一起動、フェーズは `claimPhase` で一意発火

### アクセス量（解禁時）

T0 でカレンダー1回取得 → 未解禁なら +1s/+2s/+3s/+5s/+10s の最大5回再取得 → 予約導線。1リクエストあたり概ね10〜20ページ遷移以内。
